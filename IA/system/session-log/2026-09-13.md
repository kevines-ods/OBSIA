# Session du 2026-09-13 — choix du harness pour le coffre

Question de l'utilisateur : quel harness héberger sur sa VM Fedora, avec sept
critères posés d'emblée — providers locaux et API, administration de l'hôte
Proxmox et du PC de jeu, accès depuis le PC et le téléphone sans perdre le fil,
MCP dont GitHub, équipe d'agents, multi-sessions. Cinq candidats confrontés sur
documentation ; aucun installé.

## Décisions prises

- **OpenCode retenu**, en mode serveur sur la VM Fedora, joint par réseau
  privé et non publié sur l'internet. Le motif détaillé et les écartés vivent
  dans `mémoire/assistant/choix-du-harness/2026-09-13-opencode-retenu-et-les-ecartes.md`.
- **Le harness se lancera depuis la racine du coffre parent**, pas depuis le
  dépôt : première voie du §7.6, qui rend le serveur MCP `coffre-parent`
  inutile. Contrepartie assumée : `CLAUDE.md` n'est plus chargé
  automatiquement, et doit être listé dans la configuration.
- **Les tâches restent `exécutant: local`.** Aucun planificateur documenté côté
  harness : l'invariant du §12 n'est pas menacé.
- **La fiche d'adaptation passe en v2** et cesse d'être un squelette de dix
  lignes : elle porte désormais la carte agent → agent, la traduction de
  `read_only: true` en permission du moteur, le motif MCP par agent, et la
  réserve de sécurité sur l'exposition du service.
- **Rien n'est changé dans les règles.** Aucun nom de harness n'entre dans le
  contrat ni dans un skill : la décision vit en mémoire, l'intégration dans le
  dossier des adaptateurs, qui existe pour ça.

## Questions restées ouvertes

- **Rien n'est installé.** La décision est une direction ; la VM reste à
  monter, et l'usage peut l'infirmer.
- **La syntaxe `@` d'import de `CLAUDE.md`** est-elle résolue par ce harness ?
  Contournée d'avance en listant les fichiers de `IA/system/` un par un, donc
  sans conséquence — mais la réponse simplifierait la configuration.
- **Les clients mobiles sont des projets tiers.** Point soulevé en séance :
  l'un d'eux, publié sur un magasin d'applications, paraît officiel. Vérifié —
  il ne l'est pas, la documentation du projet n'énumère aucune interface
  mobile. C'est le client libre également distribué sur F-Droid, donc
  auditable, ce qui en fait le moins mauvais choix parmi les quatre qui
  circulent. Le navigateur reste le repli, et ce repli n'a pas été essayé.
- **L'arbitrage OpenClaw peut être rouvert** si l'utilisateur juge le confort
  du téléphone plus lourd que le risque. Ce serait sa décision, pas un oubli.
